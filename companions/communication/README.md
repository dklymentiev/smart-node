# communication

Channel adapters for a Smart Node -- the **transport layer** of the
communication runtime model (`communication-runtime-model.md`).

An adapter does exactly one thing: move messages between a channel and
the **messages registry**. No reasoning, no LLM, no replies of its own.
Adding a channel is a new adapter plus a `channel_type` value -- zero
structural change.

This component lives inside the `smart-node` installer repo (a recorded
exception to the one-repo-per-component rule -- it has no consumer
outside a Smart Node). The `communication` companion installer
(`companions/communication.sh`) installs it; this
directory is the source, not a vendored snapshot.

## Layout

```
communication/
  adapters/
    telegram/   transport.py (Bot API) + adapter.py (long-poll daemon)
    email/      transport.py (IMAP/SMTP) + adapter.py (cron poll pass)
  common/
    config.py   environment-driven settings
    db.py       the messages-registry writer
  dispatch.py   the realtime trigger -- registry -> brin -> reply
  requirements.txt
```

## The contract

Every adapter writes the node's `messages` table (B02 core schema, the
cross-component contract -- in the `smartnode` core DB):

- **inbound**: receive from the channel -> `db.record_inbound(...)`. The
  B02 `AFTER INSERT` trigger seeds a `message_state` row (status `new`);
  brin / the secretary pick it up from there.
- **outbound**: `deliver(...)` sends on the channel, then
  `db.record_outbound(...)`. Called by the dispatch layer (the
  secretary / brin) -- not by the adapter itself.

Deduplication is the `(channel_type, external_id)` unique index. Each
adapter mints a stable per-channel `external_id`:

| channel  | `external_id`         | ingestion        |
|----------|-----------------------|------------------|
| telegram | `chat_id:message_id`  | long-poll daemon |
| email    | RFC822 `Message-ID`   | cron poll pass   |

## The dispatch layer

Adapters only ingest -- they land inbound rows and stop. `dispatch.py`
is the realtime trigger that closes the loop: it scans
`message_state` for `new` inbound rows, POSTs each to **brin** (the
brain-router, reached over loopback HTTP), and delivers the reply on the
originating channel via that adapter's `deliver()`. State advances
`new -> routed -> processed` (or `failed`, with the error recorded).

It is the "dispatch layer" the outbound contract above refers to -- a
pure registry consumer plus a brin HTTP client, channel-agnostic via a
`channel_type -> deliverer` map.

## Running an adapter

```
# telegram -- a long-running daemon
python -m adapters.telegram.adapter

# email -- one poll pass, invoked by cron
python -m adapters.email.adapter

# dispatch layer -- a long-running daemon (needs brin reachable)
python -m dispatch
```

Run from this directory so `common`, `adapters` and `dispatch` resolve
as packages.

## Configuration

All settings come from the environment (the companion installer supplies
them via a systemd `EnvironmentFile`; a sibling `.env` works for a
standalone run). `common/config.py` documents each.

- shared: `SMARTNODE_DB_DSN` (default `dbname=smartnode`, peer auth),
  `COMMUNICATION_STATE_DIR`
- telegram: `TG_TOKEN`, `TG_CHANNEL_ID`
- email: `IMAP_HOST/PORT/USER/PASSWORD/FOLDER`,
  `SMTP_HOST/PORT/USER/PASSWORD/FROM`, `EMAIL_CHANNEL_ID`
- dispatch: `BRIN_API_KEY` (required -- generated by the dispatcher
  companion), `BRIN_API_URL` (default `http://127.0.0.1:8101`),
  `DISPATCH_INTERVAL` (default `3`, seconds)
