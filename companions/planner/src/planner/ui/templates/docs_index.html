Reference enums

All check-constraint vocabularies in one place. Adding a value requires a migration.

priority (tasks.priority)

criticalDrop-everything. Production outage / SEV-1.
highImportant but not on fire. Plan it into the current sprint.
mediumDefault. Normal queue.
lowNice to have. May sit forever.

complexity_hint (tasks.complexity_hint)

simpleHours. One file, one place, obvious change.
moderateA day or two. Touches a couple of components.
complexA week or more. Crosses subsystems or needs design.
unknownCan't size without spike. Use sparingly — prefer reassessing.

blocked_reason (tasks.blocked_reason)

task_dependencyWaiting on another task in this planner. blocked_by points at it.
external_approvalWaiting on a person/system outside the planner. Use external_detail.
scheduled_timeCannot start until a specific date/time arrives (release window, embargo).

Extension points

Planner is intentionally agnostic about what kinds of work, communication, or events are attached to a task. Three tables are free-form by design — any external service can write into them without a schema change. task_notifications is the reverse channel: Planner writes, downstream services read.

Bucket Direction Why it's open-ended Typical use
task_log inbound (services write) action is plain text with no CHECK-constraint. Append-only by convention. Audit / activity events: created, status, tag_added, email_received, build_failed, review_passed...
task_links inbound kind is plain text; URL is just a URL. Planner has no resolver — clients decide what to do with the link. Pointers to anything: PR, deploy, dashboard, document, recording, email thread, support ticket, CI run.
task_comments inbound content is plain text. comment_type is optional and free-form (no enum). Human conversation, agent narration, structured payloads serialized as text.
task_notifications outbound (services read) event_type free-form. payload is JSONB. notify_target is a free-form identifier the consumer interprets. Planner writes on transitions. Subscribers poll WHERE fired_at IS NULL, deliver, set fired_at.

Three levels of integration

Pick by how much structure you need. There is no wrong choice — you can mix.

Level 1

Just attach a URL

Service has a permalink to its own UI. Drop it in task_links and stop.

POST /api/v1/tasks/1217/links
X-API-Key: <service-key>
{
  "kind": "email",
  "url":  "mail://thread/abc123",
  "label": "Re: Lander Journal"
}

No structure, no search inside. UI shows a link with a kind label.

Level 2

Comment as the service

Service narrates into the task timeline with its own actor.

POST /api/v1/tasks/1217/comments
X-API-Key: <service-key>
{
  "content": "[IN 04/12 11:49 from Sonat] Re: Lander Journal — acknowledges and approves",
  "comment_type": "email"
}

Text-only payload. UI can filter / colour by comment_type.

Level 3

Own table, FK to tasks.id

You need structured fields (from, subject, direction, thread_id). Add a migration:

CREATE TABLE task_emails (
  id          SERIAL PRIMARY KEY,
  task_id     INT NOT NULL
              REFERENCES tasks(id)
              ON DELETE CASCADE,
  direction   TEXT,   -- in / out
  from_addr   TEXT,
  subject     TEXT,
  body        TEXT,
  received_at TIMESTAMPTZ
);

First-class entity. Searchable, indexable, own UI section.

Wiring an external service

  1. Register an actor for the service. 
    INSERT INTO actors (id, display_name, type)
VALUES ('mail-service', 'Mail Service', 'agent');
  2. Issue an API key via /ui/keys (bind to mail-service). Capture the plaintext shown once.
  3. Service writes via REST (X-API-Key header). Audit attribution flows naturally: every comment / link / log row carries actor = 'mail-service'.
  4. For the reverse direction, the service polls task_notifications (or a future GET endpoint over it) WHERE fired_at IS NULL, processes the event, then stamps fired_at = now(). Planner is unaware of consumers — add or remove any number of them without code changes.

What is and isn't there today

  • Available now: POST/GET for comments, links, tags, commits, relations; GET for log.
  • Missing: POST endpoint for task_log. Currently only the repo layer writes there. To let external services emit arbitrary timeline events (email_received, build_failed), add POST /api/v1/tasks/{id}/log.
  • Missing: GET endpoint for task_notifications. Today consumers must read PostgreSQL directly.

Guarantees the schema gives

  • actor is an FK to actors.id in task_log and task_comments.author — unknown actors are rejected at the DB layer (no anonymous writes).
  • task_log rows are intended append-only. Nothing in the schema enforces it (no trigger), but the repo never updates or deletes them. Treat as immutable.
  • All child tables (task_comments, task_log, task_tags, task_links, task_relations, task_commits, task_notifications) ON DELETE CASCADE from tasks — deleting a task cleans up its history.
  • api_keys.key_hash is sha256 of plaintext. Plaintext shown once at creation, never stored.
